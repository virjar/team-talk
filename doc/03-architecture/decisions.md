# 架构决策

本章只记录会影响多个模块、且不能从代码直接理解的长期取舍。实现细节、故障经过和临时计划不在
这里维护。

## D1 · 模块化单体而非微服务

**上下文**：目标是单组织万级用户，部署方通常没有专职平台团队。

**决定**：服务端以单 JVM 进程运行，内部按领域服务和基础设施分层。

**结果**：部署和一致性更简单；单进程容量与故障域需要通过监控和备份管理。只有真实容量数据证明
必要时才拆分。

## D2 · 自定义确定性二进制协议

**上下文**：客户端和服务端共享 Kotlin 模型，需要稳定字段顺序、紧凑帧和可编译验证的 RPC ID。

**决定**：核心实时通道使用自定义 frame、IProto 和 IDL 生成 RPC，不使用 JSON 作为内部 IM 协议。

**结果**：类型和字节布局清晰、依赖少；不兼容变化需要协议版本管理，其他语言 SDK 必须按规范实现
编解码。HTTP 管理 API 仍可使用 JSON。

## D3 · 本地优先 UI

**上下文**：多设备、断线和页面切换会让“每个页面自己请求远端”产生状态分叉。

**决定**：UI 观察 LocalCache；服务端事件是远端变化进入本地的主路径。

**结果**：离线浏览和页面一致性更好；每个新远端字段都必须设计事件、缓存和恢复路径，不能只加一个
页面 API。

## D4 · 所有者驱动生命周期

**上下文**：连接断开、token 失效、登出和窗口销毁是不同层次事件。

**决定**：应用、用户和连接形成三级所有权，销毁从所有者向下传播。

**结果**：普通断线不会清登录态；认证失败也不会被无限重连掩盖。组件 `close/destroy` 必须幂等。

## D5 · 完整快照事件与 at-least-once

**上下文**：增量 patch 对版本、顺序和漏事件高度敏感。

**决定**：持久化 NOTIFY 尽量携带完整对象快照；客户端成功处理后才推进游标。

**结果**：重复事件可以 upsert，恢复简单；payload 比 patch 大，事件交付必须分页。Presence 等
瞬时状态可以明确豁免持久化。TTL 清理只能在协议能明确要求并验证 full resync 后启用；
当前开发基线为避免静默 cursor gap，接受 `sync_events` 无界增长。持久游标由每个 uid 独立连续分配，
不能用并发事务中的全局数据库序列充当提交顺序。

## D6 · 已读使用单调水位

**上下文**：逐消息逐用户的已读记录会带来大量写放大和合并复杂度。

**决定**：按用户/会话保存 `readSeq`，只允许增长。

**结果**：未读可由序列差计算，乱序更新易合并；不能表达“跳过中间消息只读后面某一条”的稀疏
状态，这也不是当前产品需求。

## D7 · 附件由内嵌服务拥有

**上下文**：私有化部署需要稳定的数据所有权和统一权限，任意 URL 会绕过存在性与访问校验。

**决定**：文件消息保存规范化相对路径；上传下载只走 TeamTalk HTTP 端点；发送前服务端确认附件
存在。

**结果**：SDK 成功语义可靠，fork 能完整拥有数据；MessageStore 随消息原子维护附件到会话的反向
索引，下载端点同时校验 access token 与当前成员资格。部署方若接入外部对象存储，应在 FileStore
实现层适配，不能改变消息契约为任意 URL 或公开对象地址。

## D8 · PostgreSQL、RocksDB 与 Lucene 分工

**上下文**：关系查询、顺序消息、二进制文件和全文索引有不同访问模式。

**决定**：关系数据用 PostgreSQL；消息和文件用 RocksDB/文件系统；搜索用可重建 Lucene。

**结果**：每种存储匹配工作负载，但不存在跨存储事务。服务端必须通过写入顺序、幂等和重建工具
保证恢复。

## D9 · Android 与 Desktop 不共享导航

**上下文**：早期把移动端页面直接搬到 Desktop 造成全屏资料页、奇怪的中栏动作和不符合桌面的
返回逻辑。

**决定**：共享业务屏幕片段与主题，不共享平台导航和容器。

**结果**：部分 UI 代码重复是可接受成本；平台体验和窗口生命周期更清晰。

## D10 · 单一部署配置

**上下文**：profile、flavor、命令行开关和运行时服务器选择会产生未经测试的配置组合。

**决定**：客户端默认值、部署和真实验收统一读取 `gradle/deployment.json`；fork 修改该文件。

**结果**：构建产物目标明确、可复现；同时连接多个组织服务器不在当前产品模型内。

## D11 · 测试以风险分层

**上下文**：业务系统的大部分错误来自跨模块和跨客户端协作，仅靠单元测试无法覆盖。

**决定**：本地测试覆盖协议、算法、存储和确定性边界；真实部署验收覆盖业务闭环；客户端用可观测
语义接口做交互验证。

**结果**：反馈速度与真实性兼顾；远端验收需要维护稳定测试实例和可清理账号数据。

## D12 · 协议契约独立于客户端 SDK

**上下文**：早期 `shared` 同时包含 wire、模型、RPC 生成物、客户端连接、SQLite、Repository 和 Bot；
服务端为了复用协议而依赖整个客户端 SDK，甚至能在生产代码中误用客户端类型。

**决定**：建立独立 `protocol` KMP 模块，承载线上契约、传输模型、消息体、RPC IDL、认证纯规则和
HTTP DTO。`shared` 作为客户端 SDK 依赖它；服务端生产代码只依赖 `protocol`，测试对端才依赖
`shared`。

**结果**：服务端与客户端实现之间的越界由编译器阻止，协议可以单独测试和发布，未来其他语言 SDK
也有清晰入口。代价是增加一个模块，并要求共享规则先判断属于“线上契约”还是“客户端策略”。

## D13 · 领域端口与持久化消息投影

**上下文**：早期领域服务直接依赖 Exposed、RocksDB、Lucene、ClientRegistry 和 RPC Stub；消息写入
三种存储时也没有可恢复中间状态。任一投影失败后，幂等重试只返回旧 seq，会留下搜索、会话或
同步事件缺口。

**决定**：领域层定义 Repository、MessageSearch、EventPublisher、AttachmentCatalog 和 OnlineSessions 端口，
基础设施实现它们。消息本体、clientMsgId 索引与待投影 outbox 在 RocksDB 中原子提交；所有
跨存储投影成功后才清除 outbox。

**结果**：领域规则可以用内存适配器单测，基础设施不再渗入业务 API；进程重启和幂等重试能补齐投影。
代价是 at-least-once 补偿可能重复事件，下游必须保持 upsert 幂等。

## D14 · 客户端按业务能力组织会话状态

**上下文**：早期 `AppDataState` 同时持有会话、设备、黑名单、好友申请、资料、群成员、邀请链接、
搜索、转发和二十余个动作。新增页面会继续扩大它，平台壳只能依赖一个不透明的全局对象，状态所有者
和测试边界都不清楚。

**决定**：`AppDataState` 降为客户端会话的组合根，只拥有共享 ViewModel、feature controller、协程
生命周期和统一错误出口。账户、群组、发现等用例按业务能力进入独立 controller；平台导航仍由
Android/Desktop 壳持有。

**结果**：新增功能有稳定落点，平台壳能按能力依赖，业务状态不会继续集中到单一对象。Controller
当前仍通过 `ClientSession` 使用 SDK；当单个能力需要独立测试或复用时，再把所需 Repository 收窄为
显式构造参数，避免预先制造大量一方法接口。

## D15 · 组织目录是部门群成员事实源

**上下文**：办公组织会频繁调岗、兼任和拆分。如果部门群与组织目录分别维护成员，二者必然长期
分叉；跨 PostgreSQL 表和消息/会话投影也无法依赖一个全局事务完成。

**决定**：组织成员只写 OrganizationMembership；部门群使用稳定的组织节点 ID 作为 chatId，并由
OrganizationService 根据节点子树幂等 reconciliation。受管群拒绝普通成员生命周期和成员修改接口。
组织事实先提交，群投影随后收敛，服务启动时重放所有受管群。

**结果**：调岗和部门移动可以自动反映到群，崩溃不会永久产生第二个部门群。代价是部门群不能像
普通群一样任意加人或改名；临时协作应建立普通群，而不是破坏组织事实源。

## D16 · 通知机器人使用受限服务身份

**上下文**：让外部系统保存普通用户密码或直接调用内部消息协议，会获得过大权限，也无法在管理端
准确发现、轮换和撤销。

**决定**：AutomationBot 关联不可密码登录的 User 服务身份；高熵 token 只保存哈希，每个群使用显式
grant。HTTP 入口把 bot 与目标群编码在服务端签发的路径中，请求正文只接受 Markdown，并可通过独立
`Idempotency-Key` Header 启用重试去重；调用方不能在正文中改写目标群。发送复用 MessageService
完成成员、禁言、附件和消息投影语义。停用先撤权再移出群，启动时按 grant 修复成员投影。

**结果**：机器人消息与普通消息共享显示、历史、搜索和 ACK 语义，外部系统不需要数据库或 TCP
权限。当前仅是单向通知入口并使用进程内每 bot 限速；持久化审计、分布式配额和可靠事件回调仍需在
开放平台阶段扩展。

## D17 · 办公对象独立于消息

**上下文**：Markdown 消息适合交流，但没有长期内容所需的稳定身份、独立权限、修订历史和并发坐标。
把文档伪装成超长消息会让编辑、引用、搜索和保留策略都依附聊天序列。

**决定**：Document 是企业资产域的独立聚合，消息未来只引用 `documentId`。DocumentSpace 是权限根，
用户与组织部门通过 grant 获得角色；组织成员变化在访问时实时生效。空间包含无环目录树，Document
保存 Markdown 当前快照与不可变完整修订，写入使用 `expectedRevision` 乐观锁。Chat 可以讨论文档，
但不拥有文档或决定权限。

**结果**：大部门、跨部门项目和临时团队可以按资产边界组织空间，不必复制组织树或依赖群生命周期；
文档可独立演进 ACL、评论、引用和索引，也能明确拒绝并发覆盖。代价是当前权限计算和文档拉取都发生
在服务端调用边界；实时事件、本地缓存、离线编辑、节点级例外权限与 CRDT 需要完整同步方案后再加入。
