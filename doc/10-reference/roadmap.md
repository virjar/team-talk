# 路线图

路线图只描述尚未达到的结果，不记录已经完成的月份流水账。优先级由发布风险和架构依赖决定；每一阶段必须有明确完成条件。

## 阶段一：形成可发布的私有化部署

目标是让一个 Fork 可以通过文档化配置安全、可恢复地运行，而不依赖开发者记忆。

- 将 TCP 监听端口真正接入部署与运行时配置；
- 建立版本化 PostgreSQL、RocksDB 和客户端缓存迁移策略；
- 提供备份、恢复、数据重建和容量检查工具；
- 强化管理后台认证、权限、审计和敏感操作确认；
- 补齐 TLS、反向代理、密钥轮换、日志保留和故障恢复说明；
- 建立从构建、部署、远程验收到客户端冒烟的发布门禁。

完成条件：一个没有项目历史背景的维护者可以按文档部署、升级、备份、恢复，并通过完整验收。

## 阶段二：收紧同步与可靠性边界

目标是让长离线、弱网络和多设备成为常规状态，而不是特殊故障。

- 为离线事件补发提供明确分页或持续拉取机制；
- 评估 typing 等临时事件与持久事件的分流；
- 收紧消息 seq 分配和崩溃恢复策略；
- 完善发送队列重试分类、失败可恢复性和可观测指标；
- 建立多设备并发编辑、撤回、已读和会话更新的系统测试；
- 为本地缓存制定保留、压缩、迁移和损坏恢复策略。

完成条件：断网、服务重启、长离线和多设备并发的场景可重复通过，且没有假成功或永久卡住的状态。

## 阶段三：补齐客户端产品闭环

目标是把已经确定的信息架构从“可用”提升到一致、完整和跨端可预期。

- 完成真实头像上传、加载、缓存和资料入口；
- 增加登录后的在线状态快照，完成输入中发送节流；
- 为搜索结果提供精确消息定位；
- 建立附件索引、ACL 和文件搜索；
- 在服务注册模型成熟后接入服务搜索；
- 完成交互卡片动作协议与表情回应聚合模型；
- 持续补齐 Android 系统交互和 Desktop 键盘、窗口、无障碍体验。

完成条件：核心工作流在 Desktop 和 Android 上具有一致语义，所有可见入口都有真实数据和完成路径。

## 阶段四：产品化自动化与开放能力

目标是在不绕过安全模型的前提下，让机器人、AI 和外部系统成为受治理的客户端。

- 为 `tt-agent`、CLI 和 MCP 建立稳定版本、配置与安装体验；
- 增加 bot 身份、最小权限、会话白名单、限速和审计；
- 设计带签名、重试、幂等和管理界面的 Webhook；
- 定义应用/服务注册表，作为服务搜索和群应用的事实源；
- 让自动化测试复用产品路径，同时保留协议级故障定位能力。

完成条件：外部集成无需数据库权限，可被管理员发现、授权、审计和撤销。

## 后续：评估规模化架构

只有单实例稳定性、迁移和可观测性成熟后，才进入多节点设计。需要先回答：

- 用户连接和事件如何跨节点路由；
- chat seq 和 eventId 如何一致分配；
- 文件与搜索索引如何共享或分片；
- 节点故障时未确认消息如何恢复；
- 私有化部署是否真的需要这一复杂度。

多节点不是发布前默认目标，也不能通过简单增加服务器副本实现。

## 路线图维护规则

- 已完成事项从路线图删除，并更新功能状态或稳定设计文档。
- 新需求先归入产品域与阶段目标，不为每个需求创建新的顶级文档章节。
- 只有存在清晰用户价值、依赖和验收条件的事项才进入路线图。
- 临时缺陷进入 issue 或测试场景；重复暴露的系统性问题才上升为路线图目标。
