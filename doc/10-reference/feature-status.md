# 功能状态

TeamTalk 当前处于发布前开发阶段。本文回答“现在究竟能做什么”，避免把规划中的 UI、已有数据结构和真正完成的业务闭环混为一谈。

状态定义：

- **可用**：主要链路已落地，并有对应测试或实际验收入口；
- **部分**：契约或局部界面存在，但关键闭环仍缺失；
- **计划**：产品方向明确，尚未形成可依赖契约；
- **边界外**：当前架构有意不承担。

## 核心业务

| 领域 | 状态 | 当前边界 |
|---|---|---|
| 注册、登录、凭证恢复、退出 | 可用 | 支持多设备 token；认证终态失败停止自动重连 |
| 用户资料 | 可用 | 姓名、手机号等读写和 USER_UPDATED 已接通 |
| 好友申请、接受、删除、备注、黑名单 | 可用 | 服务端是关系与权限事实源；申请支持收到/发出历史和两人 pending 精确查询 |
| 私聊、群聊和群成员管理 | 可用 | 包含角色、禁言、邀请链接、转让群主 |
| 组织架构与成员归属 | 可用 | 单组织树、用户多部门/唯一主部门；普通客户端只读，管理端写入 |
| 受管部门群 | 可用 | 节点子树是成员事实源；组织变更和启动恢复自动收敛，拒绝手工成员修改 |
| 会话列表、草稿、置顶、静音、已读 | 可用 | 本地优先展示，事件驱动收敛 |
| 文本消息 | 可用 | 统一使用 `RICH_TEXT` / Markdown，只有一条 wire 分支 |
| 编辑、撤回、回复、转发、搜索 | 可用 | 搜索结果可打开会话，但精确滚动到目标 seq 尚未完成 |
| 断线队列、重连和离线事件补偿 | 可用 | epoch 3 已持久化 FIFO outgoing、稳定 clientMsgId 及有界 SUCCESS 回执、Bot eventId delivery log；正式发布前仍需确定终态诊断/delivery history 长期压缩策略 |

## 附件与富内容

| 能力 | 状态 | 当前边界 |
|---|---|---|
| TeamTalk 文件上传与下载 | 可用 | HTTP 端点与 IM 服务同一部署；消息保存相对路径 |
| 附件发送与读取安全校验 | 可用 | 成功 ACK 前校验主文件、缩略图和元数据；下载按上传者或当前会话成员校验引用 ACL |
| 普通文件下载策略 | 可用 | 小文件静默下载，大文件点击后下载，气泡展示传输状态 |
| 图片、语音、视频与缩略图 | 可用 | Desktop 与 Android 共享消息模型，各平台提供媒体能力 |
| Markdown 富文本、mention、代码块 | 可用 | 输入和展示以 `RICH_TEXT` 为主；跨端渲染需持续回归 |
| 交互卡片 | 部分 | 发送、协议和基础渲染存在，动作回调、权限与业务路由尚未产品化 |
| 表情回应 | 部分 | wire body 与基础展示存在，缺少聚合存储、增删语义和完整交互 |

## 明确的架构边界

- 附件不使用第三方对象存储 URL 作为消息事实；外部 HTTP URL 只用于 SDK 接入展示或部署地址解析。
- 当前不是端到端加密系统。服务端需要解析消息元数据以完成存储、搜索、审核和同步；E2E 加密不是现阶段“漏做的按钮”。
- 当前按单实例私有化部署设计。多节点扩展必须先补连接路由、序号分配、事件日志和文件共享方案，不能仅增加副本数。
- 项目尚未承诺旧测试数据兼容。发布前的破坏性模型重构可以重建测试数据，但正式发布后必须通过迁移制度演进。
