# 测试与验收

TeamTalk 是多客户端、长连接、异步同步的业务系统。单元测试能证明局部规则，却不能单独证明“一条消息真的从客户端经过服务器到达另一个客户端”。因此，项目采用三层质量体系，并把真实部署作为业务验收的中心。

## 质量模型

| 层级 | 回答的问题 | 主要入口 | 典型覆盖 |
|---|---|---|---|
| 本地安全网 | 一个模块的规则是否仍然成立 | `:shared:jvmTest`、`:server:test`、客户端测试 | 编解码、状态机、存储、算法边界、组件行为 |
| 部署验收 | 完整服务和真实依赖是否协同工作 | `:server:acceptanceTest` | 认证、好友、群聊、消息、文件、数据库、搜索 |
| 客户端验收 | 用户实际看到和操作的功能是否正确 | Desktop 内置测试服务、Android UI 自动化 | 窗口、导航、输入、动画、下载、截图、跨端联动 |

三层不是相互替代关系。功能越接近业务流程，越需要向后两层移动；纯函数、编解码和边界条件仍应尽量留在本地测试中。

## 标准验证路径

一次涉及业务行为的改动，通常按以下顺序验证：

```text
编译与本地测试
    ↓
部署测试环境（服务端有改动时）
    ↓
真实部署 acceptanceTest
    ↓
启动真实客户端并执行用户流程
    ↓
核对语义状态、对端状态与截图
```

只改纯 UI 布局时可以跳过服务端部署，但仍应通过客户端截图验证。只改协议或服务端规则时，也不能仅以“编译成功”作为完成标准。

## 发布门禁

项目尚未正式发布，但每个可交付状态至少应满足：

1. 受影响模块可以编译，本地相关测试通过。
2. 协议和业务改动通过真实部署验收。
3. 用户可见改动在目标客户端上完成真实操作与截图核对。
4. 新增交互具备稳定 `testTag`；新增协议具备契约测试或验收场景。
5. 已知缺口写入[功能状态](../10-reference/feature-status.md)，不混入稳定设计文档。

测试报告属于一次执行产生的证据，应保存在 CI、测试报告目录或发布记录中；本章只描述可重复的测试制度与场景，不维护“某天通过了多少项”的历史台账。
