# 测试与验收

TeamTalk 是多客户端、长连接、异步同步的业务系统。测试优先从稳定的业务入口验证模块协作与用户结果，
不要求为每个内部类、方法或分支配套单元测试。代码评审和编译负责简单、直接的内部实现，少量确定性
测试补足难以从完整业务链路稳定触发的故障窗口。

## 质量模型

| 层级 | 回答的问题 | 主要入口 | 典型覆盖 |
|---|---|---|---|
| 模块集成 | 业务入口与真实依赖是否协同工作 | `:server:server:test`、`:client:shared:jvmTest`、客户端持久化测试 | PostgreSQL 事务、TCP 链路、真实 SQLite、存储重启与恢复 |
| 少量单元与协议契约 | 哪个易错规则或故障窗口需要单独固定 | 协议测试及上述任务中的确定性用例 | wire 格式、复杂解析、并发时序、难以稳定触发的回归 |
| 部署验收 | 完整服务和真实依赖是否协同工作 | `:server:server:acceptanceTest` | 认证、好友、群聊、消息、文件、数据库、搜索 |
| 客户端验收 | 用户实际看到和操作的功能是否正确 | Desktop 内置测试服务、Android UI 自动化 | 窗口、导航、输入、动画、下载、截图、跨端联动 |

测试类型由实际依赖与断言决定，不由目录名决定：使用真实 PostgreSQL、SQLite 或 TCP 的用例不会因为
放在 `src/test` 就变成单元测试；调用一个纯函数的测试也不会因为放在 `e2e/` 就变成端到端测试。

## 取舍原则：轻单元、重集成与端到端

- **默认不新增内部单测**：简单 CRUD、字段映射、常量声明、参数转发、UI 装配由评审、编译及相应业务
  流程覆盖。不要通过反射断言私有字段、类型继承或内部调用步骤，给合理重构增加无意义的失败。
- **保留需要精确定位的复杂规则**：例如提交与回执之间的崩溃、并发落盘/关闭、游标去重、复杂解析。
  必须能说清具体失败方式；名字含“安全”“状态机”“预算”不是自动保留理由。
- **真实 bug 在最合适的层补一个回归**：优先现有集成/E2E 场景，只有上层难以确定性触发或定位时才补
  最小局部用例。不要在 helper、service、repository、UI 四层重复穷举同一事实。
- **集中保护跨端协议契约**：保留实际 wire 编解码、固定字节/ID 与错误输入行为；不为每个 DTO 的
  构造、默认值或普通 getter 建独立测试。
- **以维护价值决定删减**：上层已经检查相同行为时删除重复断言；简单实现可以直接交给评审和业务
  验证，不必为删掉一个单测再新造一个测试。复杂可靠性场景不能仅凭“CI 会跑”就删除。
- **禁止为测试单独开发服务实现**：`shared-testkit` 仅保留 e2e/acceptance 需要的
  `FakeLocalCache` / `FakeRpcInvoker`，永不作为产品依赖，禁止新增单元测试专用 Fake，
  禁止为 Fake 编写自测。
- 测试数、文件数与内部行覆盖率不是目标。测试代码也应能局部阅读，不通过改名、合并到巨型文件或
  新增通用测试框架来伪装精简。

## CI 的实际覆盖

`ci.yml` 在 push/PR 时通过 Gradle 运行管理后台生产构建、客户端编译、架构检查、服务端真实
PostgreSQL/TCP 集成、SDK SQLite 及保留的协议/客户端局部测试。管理后台使用 `:server:admin:check`，
和本地共用锁文件安装、TypeScript 检查与 Vite 构建链，无需 CI 单独配置 Node.js。
`acceptance.yml` 是手动触发的远程验收，`release.yml` 在部署后执行同一业务
验收。Desktop 与 Android 的真实 UI 验收仍需按平台操作流程单独运行；不能把一次人工或任务内 UI
验收当作每次提交都会运行的自动回归，也不能以 SDK 验收替代输入框、窗口和系统交互。

## 开发者预览版的轻量入口

少量内测使用 `./gradlew :server:server:previewSmokeTest` 检查既有核心业务，不执行重启、强杀、容量
或组织管理场景。它复用完整远端验收中的九个场景，仍使用真实服务和 SDK；范围与候选安装包的短路径
检查见[预览版指南](../01-getting-started/developer-preview.md)。完整发布继续使用下面的验收制度。

## 标准验证路径

一次涉及业务行为的改动，通常按以下顺序验证：

```text
编译与本地测试
    ↓
部署测试环境（服务端有改动时）
    ↓
真实部署 acceptanceTest
    ↓
启动真实客户端并执行用户流程
    ↓
核对语义状态、对端状态与截图
```

只改纯 UI 布局时可以跳过服务端部署，但仍应通过客户端截图验证。只改协议或服务端规则时，也不能仅以“编译成功”作为完成标准。

## 发布门禁

项目尚未正式发布，但每个可交付状态至少应满足：

1. 受影响模块可以编译，本地相关测试通过。
2. 协议和业务改动通过真实部署验收。
3. 用户可见改动在目标客户端上完成真实操作与截图核对。
4. 新增交互具备稳定 `testTag`；新增协议具备契约测试或验收场景。
5. 已知缺口写入[功能状态](../10-reference/feature-status.md)，不混入稳定设计文档。

测试报告属于一次执行产生的证据，应保存在 CI、测试报告目录或发布记录中；本章只描述可重复的测试制度与场景，不维护“某天通过了多少项”的历史台账。
