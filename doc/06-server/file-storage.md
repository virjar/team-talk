# 文件存储

## 1. 目标

TeamTalk 把文件服务内嵌在单体中，保证私有化部署的数据所有权和消息成功语义。消息协议只引用
FileStore 相对路径；存储实现可以演进，但不能把任意第三方 URL 暴露成核心附件身份。

## 2. 分层

```text
FileStore
├── metadata / small objects → RocksDB
├── large objects            → sharded file system
└── temporary upload         → data/file-store/tmp
```

当前阈值和压缩参数以服务端 storage 代码为准。文档不把调优值当作长期协议；调整阈值不改变
Attachment。

大文件使用两级 hash 目录降低单目录文件数。物理文件名由 storage key 决定，不使用用户上传文件名，
防止路径穿越和跨平台字符问题。

## 3. 上传

`POST /api/v1/files/upload` 使用 multipart 和 access token。服务端流程：

1. 限制请求和单文件大小，写临时文件。
2. 计算类型、size、hash 与规范化对象路径。
3. 图片/视频在源临时文件仍存在时提取元数据和缩略图。
4. 按分层策略持久化主文件与缩略图。
5. 写元数据并返回 path/url/媒体信息。
6. 在 finally 中清理未被移动的临时文件。

缩略图失败不应伪造主文件失败，但必须明确是否允许无缩略图成功，并记录可诊断日志。

## 4. 发送校验

发送文件消息时服务端当前执行以下校验：

- canonicalize path。
- 查询元数据确认主文件和缩略图存在。
- 校验 name/contentType/size 与权威元数据。
- 消息服务另行校验发送者是目标 Chat 成员。
- 全部通过后才写 Message 与返回 ACK。

SDK 结构校验只是第一层，不能替代 FileStore 查询。

当前 `FileMetadata` 已记录上传者 uid，但消息发送和公开下载端点尚未建立附件引用 ACL；因此不能把
“只有上传者可引用”写成现有保证。私有化环境如需要文件级授权，应在 FileStore 查询和下载路由统一
接入授权上下文，并增加不可枚举路径之外的真正权限校验。

## 5. 下载

`GET /api/v1/files/{path...}` 当前按 path 公开读取，根据元数据定位 RocksDB 或文件系统并流式返回。
路径由 uid 与随机标识组成，但随机性不是 ACL。响应应包含正确的
Content-Type、Content-Length、缓存与下载文件名策略。Range 支持若未实现，应在大视频体验中明确
限制，不能假设所有播放器都能随机访问。

## 6. 客户端策略

- 缩略图和小文件可以自动缓存。
- 大文件点击后下载，消息气泡显示进度和取消/重试。
- 下载完成后从本地路径打开，不重复请求。
- 媒体在应用内播放；普通文件可交给系统默认应用。
- 缓存淘汰只删除客户端副本，不改变消息 Attachment。

## 7. 运维

`data/file-store/` 是持久数据，部署同步不能覆盖。备份需要同时包含元数据 RocksDB 与大文件目录；
只备份其中一层会产生不可解析附件。

需要监控临时目录、总容量、写失败、缩略图失败、孤儿对象和下载错误率。清理孤儿文件必须有安全
窗口，避免上传后尚未发送消息的正常对象被误删。
